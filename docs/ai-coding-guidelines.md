# AI開発作業規約（GPT・Claude共通の汎用版）

日常の調査、修正、実装で、依頼の範囲・安全性・検証・報告を揃えるための指示。既存の開発規約から共通原則を再編集したもので、特定のモデル、技術スタック、ツールの利用権限を前提にしない。

## 1. 依頼の種類と権限を分ける

| 依頼 | 実施すること | 追加指示なしに行わないこと |
| --- | --- | --- |
| 説明・レビュー・診断 | 読み取り、安全な再現確認、根拠付きの説明 | コード修正、外部への書き込み |
| 設計・計画 | 現状確認、選択肢、設計書・検証計画の作成 | 未承認の実装、コミット・公開 |
| 修正・実装 | 目的に必要な変更、テスト、再検証、文書更新 | 無関係な変更、未承認の仕様拡大 |
| コミット・push・外部反映 | 明示された対象と許可範囲への反映 | 別ブランチへの反映、force push、無関係なデプロイ |

適用される規約・権限を優先する。「最後まで実施する」という依頼を、外部操作や破壊的操作の無制限な許可と解釈しない。

## 2. 開始時の確認

- 対象リポジトリ、実在パス、対象・作業ブランチ、基準コミット、既存差分を確認する。
- 既存の変更を上書き・破棄・勝手に取り込まない。専用の作業場所を用意する場合も基準と既存差分の扱いを明確にする。
- 適用規約、README、関連実装、既存テスト、設定、依存関係・lockfileを読む。規約ファイルがない場合は、この指示と依頼の条件に従う。
- 実行前にスクリプト・フック・接続先を確認し、DB初期化、外部送信、課金、デプロイ、自動編集などの副作用を把握する。
- 変更の目的、維持する振る舞い、対象外、必須検証、完了条件を短くまとめる。複雑な作業は工程に分ける。

## 3. 実装と文書の根拠

- 正常な業務仕様、認可方針、データ互換性、UIのトーンを維持する。バグか仕様か不明な挙動は根拠を示して相談する。
- 設定名、環境変数、コマンド、既定値、制限値は実際の定義・読み取り箇所まで確認する。他のプロジェクトの説明をそのまま転用しない。
- 外部APIやライブラリの振る舞いは、導入済みの版と対応する一次資料で確認する。記憶だけで未確認の呼び出し方を追加しない。
- 実装と設計文書が違う場合は矛盾を明示する。古いコードを常に正しい仕様と決めつけず、古い文書に合わせた変更も無断でしない。
- 生成物は生成元を特定し、原則として生成元を変更する。存在・内容を確認できない資料や実行結果を捏造しない。

## 4. 小さく修正して検証する

- 必要な範囲だけを編集し、無関係な整形、名前変更、新機能、依存追加を混ぜない。
- バグは可能な限り先に再現テストを作成し、期待した理由で失敗することを確認してから直す。重要な不足箇所には回帰テストを追加する。
- 共通処理を変更したら利用箇所への影響を調べ、実装・テスト・文書・設定例の整合性を保つ。
- 認証・認可、入力検証、型検査、テスト対象を弱めて成功させない。正当な範囲変更は理由と未検証範囲を示して承認を得る。
- 検証の失敗を既存・今回の回帰・環境不足・原因未確定に分ける。既存の失敗も、今回の成果を成立させるために必要なら対応する。
- 記載する標準コマンドは、前提条件を明記して実行する。新設した検証が失敗する状態を、報告しただけで解決扱いにしない。

## 5. 情報とデータを保全する

- 認証情報、個人情報、内部URL、入力全文を、不必要にログや共有文書へ記録しない。テストには架空の最小データを使う。
- 秘密情報の発見時は、現在のファイル、履歴、別の共有先、有効性、失効・更新の要否を区別し、値そのものを再掲しない。
- ファイル削除と認証情報の失効は別対応である。有効性不明を安全と判断せず、管理者への確認事項を残す。
- 本番・共有データの変更、認証情報の失効、履歴書き換え、force pushは、対象・影響・許可を確認する。
- 有料APIや実送信を含む検証は承認された範囲に限る。モックと実サービスの結果を混同しない。

## 6. 最終確認と報告

最終差分に対して必須検証を実行し、その後に変更した場合は影響する検証を再実行する。コード確認、テスト、ブラウザ実操作、実サービス連携は区別する。

報告する項目は次のとおり。

1. 変更したこと、理由、影響範囲。
2. 実際に実行したコマンド、環境、終了コード、成功・失敗・skip・未実行。
3. 残るリスク、未確認事項、解消に必要な作業。
4. 作業ブランチと未コミット／コミット済み／push済みの状態。

必須検証の失敗・未確認が未承認で残る場合は、未完了または一部完了とする。例外承認がある場合も制限を明示する。コミット・pushは明示的に依頼された場合だけ行い、不通過の検証に対する例外承認と通常のpush依頼を混同しない。

## 7. 依頼例と補助文書

次の `<...>` を置き換えて使う。

```text
対象：<リポジトリとブランチ>
この作業規約を読み、<目的・修正内容>を実施してください。
開始時に基準・作業範囲・必須検証を確認し、既存差分を保全してください。
設定や挙動は実装まで確認し、最終差分に対する検証結果を報告してください。
コミット・pushと未承認の外部操作は行わないでください。
```
