# テストファースト開発・回帰防止（汎用版）

新しい振る舞いと不具合修正を、期待する結果の定義、失敗するテスト、最小限の実装、再検証の順に進める。既存のテスト方針から、固有のコマンドや実装例を除いて再編集した指示。

## 1. 最初に確認すること

- 対象の仕様、既存テスト、テストランナーの設定、実際の実行コマンドを読む。他のプロジェクトのコマンドをそのまま使わない。
- 変更前の成功・失敗・skip・未実行を記録し、今回追加するテストと既存の状態を区別する。
- テストの副作用、接続先、DB初期化、実メール送信、有料API、ファイル削除などを確認する。
- DBやストレージの変更には、確認済みの専用テスト環境を使う。接続先が曖昧なまま破壊的な初期化を実行しない。
- 期待結果は仕様から定義する。現在の実装や、その時に返った値をそのまま正解にしない。

## 2. Red：期待した理由で失敗させる

1. 入力、前提、利用者の権限、期待する出力と副作用を短く定義する。
2. 不具合を再現する最小のケース、または新機能で保証する振る舞いのテストを作る。
3. 修正前の実装でテストを実行し、失敗の原因を確認する。
4. 対象の挙動ではなく、設定不足、モジュールの読み込み失敗、DB接続失敗などで落ちている場合は、再現成功と扱わない。
5. 修正前から通る場合は、再現条件やアサーションが適切か調べる。無理に失敗させるためだけの条件を足さない。

テストの追加前に修正してしまった場合や、自動再現が困難な場合は、その事実と限界を明記する。失敗を確認したと偽らず、安全な再現方法または代替検証を検討する。

## 3. Green：最小限の修正で通す

- 原因に必要な変更だけを行い、まず対象テストを成功させる。
- 成功させるためだけに、認証・認可、入力検証、エラーハンドリングを緩めない。
- テスト対象を除外したり、根拠なく期待値・スナップショットを更新したり、型エラーを抑制したりしない。
- 期待値の誤りが見つかった場合は、仕様の根拠と修正理由を示す。実装を維持するためだけの変更にしない。
- 関連する既存テストも実行し、別の利用箇所を壊していないか確認する。

## 4. Refactor：成功を維持して整理する

- 振る舞いを維持しながら、必要な重複排除・可読性の改善を行う。
- 実装の内部構造に依存し過ぎたテストは、外から観測できる結果や重要な契約を中心に見直す。
- 共通処理やテストヘルパーの変更は、影響するテスト群でも確認する。
- 整理後に再実行する。整理前の成功だけで最終差分を検証済みにしない。

## 5. 優先して追加するケース

| 領域 | 確認すること |
| --- | --- |
| 認証 | 認証が必要な操作で未認証アクセスが拒否される。公開操作の例外は仕様に基づいて扱う |
| 認可 | 所有者・他ユーザー・他テナント・管理者などの境界と、拒否時に副作用が発生しないこと |
| 正常系 | 出力の構造・値、保存データ、状態遷移、副作用が契約どおりであること |
| 入力検証 | 必須項目、形式、null・空値、境界値、最大件数・サイズ、不正データ |
| 障害と復旧 | 外部障害、タイムアウト、部分失敗、ロールバック、再実行の安全性 |
| 非同期・競合 | 二重送信、遅い応答、順序逆転、中止、同時更新、冪等性 |
| AI・キャッシュ | 呼び出し回数、重複排除、再試行上限、失敗・空結果、失効、利用者間の分離 |

HTTPステータスや認証方式を一律に決めつけず、対象APIの契約に沿って検証する。アサーションがないテストや、テスト件数だけをカバレッジの根拠にしない。

## 6. モックとテスト環境

- モックは外部依存の境界に置き、成功だけでなく失敗・遅延・不正応答も確認する。
- 認証・認可や検証対象の処理そのものをモックで無条件成功に置き換えて、確認済みとしない。
- 実サービスへ接続しない検証では、接続が遮断・差し替えされていることも確認する。ダミーキーを設定しただけで外部通信がなくなると仮定しない。
- 時計、乱数、環境変数、グローバル状態、モックの残存などを管理し、各テストが独立して実行できるようにする。
- 後始末はそのテストが作成・所有する資源だけを対象にする。失敗時にも終了するようにし、他のデータを削除しない。
- 資格情報や実顧客データをテスト・ログへ持ち込まない。外部課金・送信は事前承認された範囲に限定する。

モックの成功は実サービス連携の成功を意味しない。AI呼び出し回数の検証と、実トークン費用の測定も分けて報告する。

## 7. 軽量検証と最終検証

- 作業中は対象・関連ユニットテストを中心に短いサイクルで実行する。
- DBスキーマ、認証・認可、外部連携、共有処理を変える場合は、作業途中でも必要な統合検証を行う。
- 最終差分では、対象プロジェクトで定義した必須検証を実施する。lint、typecheck、関連・全体テスト、build、必要なAPI・DB・実操作確認を区別する。
- フル検証に環境や権限が必要なら、その条件を準備または確認する。未実行の検証を成功に置き換えない。
- 不安定なテストは、失敗ログと条件を残して原因を調べる。再実行して一度通ったことだけで解決済みにしない。
- 新設・文書化した検証コマンドが既存エラーで失敗する場合も、未解決である。必要な修正か、範囲・例外の合意を行う。

## 8. 記録と完了判定

| 段階 | 残す記録 |
| --- | --- |
| 修正前 | 再現条件、実コマンド、失敗理由、既存の検証結果 |
| 修正後 | 修正内容、対象テストの結果、関連機能の回帰確認 |
| 最終差分 | 環境、実コマンド、終了コード、成功・失敗・skip・未実行、除外・モックの範囲 |

必須検証が失敗・未確認のままなら、未完了または一部完了として報告する。明示的な例外承認があっても、制限と残るリスクを記載する。コミット・pushは別途指示に従い、通常の反映依頼を失敗の例外承認とみなさない。

## 9. 依頼例

```text
対象：<リポジトリとブランチ>
問題・追加する振る舞い：<再現条件と期待結果>
このテストファースト手順に従い、修正前に期待した理由で失敗するテストを作ってください。
最小限の修正後に対象・関連テストを再実行し、最終差分の必須検証まで行ってください。
各段階の実コマンド・結果・未確認事項を報告してください。コミット・pushは行わないでください。
```
