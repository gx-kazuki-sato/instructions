# 設計先行ワークフロー（汎用版）

複雑・曖昧な変更や、仕様・権限・データ・外部連携への影響が大きい作業で、設計と確認を実装より先に行う。既存の設計先行、意思決定記録、作業ログに関する指示を、プロジェクト固有の構成を除いてまとめたもの。

## 1. 適用と開始条件

- 目的や期待する振る舞いが曖昧、複数案がある、複数コンポーネントに影響する場合に使う。
- 受け入れ条件が明確な小さな不具合修正に、形式だけの大きな設計書を要求しない。必要な記録の規模はリスクに合わせる。
- 「設計・計画だけ」の依頼なら、その成果物を提示したところで止める。実装・コミット・外部反映の許可まで得たことにしない。
- 設計書の保存先と命名は、対象リポジトリの既存構成・規約に合わせる。存在しないファイルを、既存資料として引用しない。

## 2. 現状と問題を明確にする

1. 関連する仕様、実装、テスト、既存の設計判断、直近の作業記録を確認する。
2. 解決する問題、利用者、現在の挙動、期待する挙動、対象外を整理する。
3. 事実、仮定、未確認事項を分ける。安全に調査できることは調べ、結果を変える重要な不明点だけ質問する。
4. 関係する画面・API・データ・ジョブ・外部サービスと、影響を受ける利用箇所を特定する。
5. 維持すべき互換性・認可・データ保持、利用できる検証環境、費用・権限の制約を確認する。

## 3. 設計書に残すこと

以下を基本とし、変更の規模に応じて簡潔に記録する。

```text
目的・解決する問題
現状と根拠となる実装・検証結果
対象範囲・対象外
要件・受け入れ条件
前提・制約・未確認事項
選択肢と比較、採用案と採用しない案の理由
変更する公開インターフェース・データ・権限
実装手順と依存関係
検証方法と必要な環境
移行・展開・ロールバックと運用への影響
残るリスク・承認が必要な事項
```

- 選択肢は効果、変更リスク、運用負担、検証可能性、戻しやすさで比較する。新技術の採用を目的にしない。
- 受け入れ条件は、操作・入力・期待結果・確認方法が分かる形にする。「使いやすい」「安全」といった言葉だけで終わらせない。
- 関係が複雑な場合だけ、最小限の構成図・データフロー・時系列を使う。図を増やすことを設計の充実と扱わない。
- 重要な設計判断は既存のADRなどの仕組みに記録する。ADRは設計判断の記録であり、採用理由と影響を後から追えるようにする。
- 文書の状態は提案・承認済み・置き換え済みなどを区別する。必須のメタデータや番号付けはプロジェクトの規約に従う。

## 4. 合意してから実装する

- 推奨案、代替案、リスク、未確定事項、承認が必要な操作を短く提示する。
- 仕様・認可・保存方針・大きな互換性変更は、必要な合意を得てから実装する。
- 設計書を作ったことと、その設計が承認されたことを区別する。通常の進捗確認や返答の省略を承認と解釈しない。
- 設計書の保存と、Gitへのコミット・pushは別の操作として扱う。先に設計書をコミットする運用が必要でも、許可範囲を確認する。
- 承認不要の読み取り・検証・低リスクな準備は進められるが、設計承認待ちを理由に未承認の実装へ進まない。

## 5. 実装中の記録と設計変更

作業記録には、適用する設計判断、完了した作業、実際の検証、未解決事項、次に行う安全な作業を残す。チャットだけを唯一の記録にしない。

| 記録 | 内容 |
| --- | --- |
| 変更内容 | 変えた振る舞い、影響する実際のファイル・インターフェース |
| 検証 | 実コマンド、条件、終了コード、結果・証拠 |
| 判断 | 参照する設計書、変更理由、新たな仮定・リスク |
| 残作業 | 未確認、承認待ち、次の作業 |

実装中に前提が崩れた場合は設計を更新する。大きな方針変更は再度合意を得る。過去の判断を無言で書き換えず、修正履歴や置き換え関係を残す。設計の理由は参照で共有し、作業記録へ同じ説明を何度も複製しない。

認証情報、個人情報、内部接続先、未加工の業務入力やモデル出力を文書へ記録しない。公開範囲に応じて、例示と証拠を必要最小限にする。

## 6. 終了時の確認

- 設計だけの依頼では、設計成果物・未確定事項・次に必要な承認を示す。実装や動作確認まで終わったと報告しない。
- 実装まで含む依頼では、受け入れ条件を最終変更に対して検証し、実装・文書・設定の整合性を確認する。
- 必須検証が失敗・未確認なら、未完了または制限付きの状態を明示し、必要な作業と承認を示す。
- 設計上の期待、モックの結果、実環境での検証を分ける。成果物の実在パスと内容を確認してから案内する。

## 7. 依頼例

```text
対象：<リポジトリとブランチ>
課題：<解決したい問題>
この設計先行ワークフローに従い、現状・選択肢・推奨案・受け入れ条件をまとめてください。
実装や外部反映はまだ行わず、実装前に確認が必要な判断を提示してください。
設計書の実在する保存先と、残る不明点を報告してください。
```
